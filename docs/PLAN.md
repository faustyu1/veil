# Veil — план развития (скорректированный)

Документ переписывает исходный roadmap с учётом того, что реально лежит в
репозитории. Порядок приоритетов сохранён (безопасность → ядро → Remnawave →
балансеры → маршрутизация → UI), но часть пунктов переформулирована: несколько
исходных утверждений не соответствовали коду, а два «идеальных» решения
упираются в платный Apple Developer Program и поэтому не могут быть базовым
вариантом.

---

## 0. Поправки к исходному аудиту

Что подтвердилось при чтении кода:

| Утверждение | Статус | Где |
| --- | --- | --- |
| `NOPASSWD` в sudoers | **верно** | `Scripts/install-helper.sh` пишет `/etc/sudoers.d/xrayclient` |
| root-скрипты `tun-up.sh` / `tun-down.sh` | **верно** | `Scripts/`, `Sources/XrayClient/Resources/` |
| предсказуемые файлы `/tmp/xrayclient-*` | **верно** | pid/state/pinned + `/tmp/tun2socks.log` |
| полный URL подписки и HWID в системном логе | **верно** | `SubscriptionFetcher.swift`, `privacy: .public` |
| подписка схлопывается в плоский список ссылок | **верно** | `SubscriptionFetcher.decode` → `LinkParser.parseMany` |
| TUN через tun2socks, процесс-инфо теряется | **верно** | `TunManager` + `tun2socks` |
| протоколы разделены между Xray и sing-box | **верно** | `CoreEngine`, два конфиг-билдера |

Что в исходном плане сформулировано неточно и как это правильно:

1. **«Не скачивать автоматически непроверенный latest» — ядра не скачиваются в
   рантайме вообще.** Xray/sing-box/tun2socks тянутся `Scripts/fetch-*.sh` на
   этапе сборки, без пина версии и без проверки контрольной суммы. В рантайме
   без верификации качаются только `geoip.dat` / `geosite.dat`
   (`GeoAssetManager`). Значит пункт распадается на два разных:
   *(a)* пин версии + SHA-256 в скриптах сборки, *(b)* проверка и атомарная
   замена гео-баз в рантайме. Механизм «обновление ядра с откатом» нужен
   только если появится рантайм-апдейтер — это отдельная, более поздняя задача,
   а не P0.

2. **HWID отправляется дважды, и ещё раз в User-Agent.** Исходный план просит
   «не добавлять HWID одновременно в URL и заголовок». Фактически сейчас он
   уходит в четырёх местах: query `hwid`, query `device_id`, заголовки `X-HWID`
   и `X-Device-ID`, плюс подстрока `hwid: …` внутри User-Agent. Последнее —
   самая неприятная утечка, потому что UA видят все прокси по пути. Правильное
   поведение: только заголовок `X-Hwid`, всё остальное убрать.

3. **HWID сейчас не «основан на серийнике», а равен `IOPlatformUUID`.** Это
   ещё хуже, чем серийник: один и тот же идентификатор получат все панели, он
   переживает переустановку приложения и позволяет связать пользователя между
   провайдерами. Замена — случайный UUID, свой на каждую подписку, в Keychain,
   с кнопкой регенерации.

4. **Network Extension из плана убран.** `NEPacketTunnelProvider` на macOS
   требует entitlement, который Apple выдаёт только по платному членству
   ($99/год) — том самом, из-за которого в репозитории до сих пор нет
   iOS-сборки (см. README). Подписки нет, поэтому NE, Developer ID и
   нотаризация не являются целью ни на одном этапе; всё строится в расчёте на
   **ad-hoc подпись**.

   Из этого следует три вещи, и они определяют архитектуру helper'а:

   - `SMAppService.daemon` полагаться нельзя — она требует валидной подписи
     бандла. Демон ставится обычным `LaunchDaemon` за один админ-промпт.
   - Клиента нельзя авторизовать по Team ID (`certificate leaf[subject.OU]`),
     потому что у ad-hoc сборки нет сертификата. Основной механизм —
     **пин `cdhash`** конкретного бинарника приложения, который установщик
     вычисляет в момент установки и кладёт в root-owned файл. Демон, не нашедший
     этого файла, не принимает соединения вообще (fail closed).
   - Пин `cdhash` меняется при каждой пересборке приложения, поэтому обновление
     Veil должно переустанавливать requirement-файл. Это цена отказа от
     Developer ID, и она осознанная.

   Сам XPC-протокол от этого не зависит: если подписка когда-нибудь появится,
   меняется только строка requirement и способ установки демона.

5. **`sing-box-lx` как главное ядро — правильное направление, но пинить форк
   опасно.** Всё, ради чего он назван (нативный TUN inbound, `find_process`,
   `process_name`/`process_path`, selector/urltest, Clash API, Hysteria2, TUIC,
   AnyTLS, ShadowTLS, WireGuard) есть в апстримном sing-box. Форк добавляет
   XHTTP и AWG2. Разумно: целиться в апстрим-совместимый конфиг, а `-lx`
   держать как drop-in замену бинарника для тех, кому нужен XHTTP — тогда
   релизный цикл форка не блокирует релизы клиента.

6. **Process-aware routing не заработает, пока TUN поднимает tun2socks.**
   `find_process` требует, чтобы TUN-инбаунд был у самого sing-box: tun2socks
   отдаёт ядру уже готовый SOCKS-поток, а PID исходного процесса на этом
   переходе теряется безвозвратно. То есть «экран Приложения» из P1 не является
   самостоятельной задачей — он физически невозможен до миграции TUN на
   sing-box. Это меняет порядок: миграция ядра — предусловие, а не параллельная
   ветка.

7. **Заголовок `routing` от Happ.** Согласен с исходным выводом и усиливаю его:
   реверс непрозрачного пресета Happ в клиент не окупается. Балансеры приходят
   в теле `XRAY_JSON` (`routing.balancers` + `observatory`), и правильный путь —
   заставить Remnawave через Response Rules отдавать нормальный `XRAY_JSON`.
   Happ-адаптер — отдельный опциональный модуль, не P0.

## 1. Фазы

      путей, с проверкой подписи вызывающего).

- [x] URL подписок и секреты — в Keychain; локальный стор — каталог 0700,

- [x] Пин версий и проверка SHA-256 для загружаемых ядер в скриптах сборки.
- [x] Проверка и атомарная замена гео-баз с откатом на предыдущую версию.

- [x] Авторизация XPC-клиента пином `cdhash`, fail closed при отсутствии

  платного Developer ID нет.

### Фаза 1 — ядро

- [ ] sing-box как основной core: нативный TUN inbound вместо tun2socks.
- [ ] Xray остаётся compatibility-core для конфигов, которые не конвертируются

- [ ] Модель конфигурации: не плоский список серверов, а полный граф

      потери неизвестных полей.
- [ ] Clash API для управления группами, `prepare → validate → switch → rollback`.

### Фаза 2 — Remnawave

- [x] Случайный регенерируемый HWID, по одному на подписку, в Keychain.
- [x] Только `X-Hwid` (+ `X-Device-OS`, `X-Ver-OS`, `X-Device-Model`),
      настраиваемый User-Agent без HWID внутри.
- [x] Полный разбор контракта ответа: `x-hwid-active`,
      `x-hwid-not-supported`, `x-hwid-max-devices-reached`,
      `subscription-userinfo`, `profile-title`, `profile-update-interval`,
      `announce`, `support-url`, `profile-web-page-url`,
      `subscription-refill-date`.
- [x] Определение формата тела: `XRAY_JSON`, `XRAY_BASE64`, `SINGBOX`,
      Mihomo YAML, plain share links; сырое тело сохраняется как есть.
- [ ] Lossless-импорт `XRAY_JSON` в полную модель конфигурации (нужна Фаза 1).

### Фаза 3 — балансеры

- [ ] Импорт `routing.balancers`, `observatory`, `burstObservatory` как есть.
- [ ] Бейдж «Управляется провайдером», запрет на случайную правку, «создать
      локальную копию».
- [ ] Локальные группы: Select, URL Test, Fallback, Round Robin, Consistent
      Hashing, Sticky, Random, least-load, weighted, цепочки.
- [ ] Health check с полным набором параметров, без разрыва живых соединений.

### Фаза 4 — маршрутизация

- [ ] Экран «Приложения» (требует Фазы 1).
- [ ] Редактор правил сайтов: domain/suffix/keyword/regex/CIDR/порт/протокол,
      AND-OR-NOT, remote rule sets.
- [ ] «Почему этот запрос пошёл сюда?» — трассировка решения маршрутизатора.
- [ ] Обязательные исключения для самого Veil, ядра, helper'а и локального API.

### Фаза 5 — DNS, цепочки, API, UI, надёжность

Содержание совпадает с исходным планом; переупорядочивание не требуется.
Единственное дополнение: локальный API должен слушать **Unix-сокет** в
каталоге 0700, а не localhost-порт — на macOS к localhost-порту может
подключиться любой процесс пользователя, и bearer-токен при этом хранится там
же, где его можно прочитать.

## 1.1. Известные ограничения того, что уже сделано

Три вещи стоит знать до того, как они всплывут в issue.

**Keychain и ad-hoc подпись.** ACL записи в Keychain привязан к подписи
приложения. У ad-hoc сборки она меняется при каждой пересборке, поэтому после
обновления Veil macOS может один раз спросить разрешение на доступ к уже
сохранённым URL подписок. Данные при этом не теряются. Если запись в Keychain
не проходит вообще, клиент не молчит и не теряет подписку — URL остаётся в
`store.json`, который лежит с правами 0600 в каталоге 0700.

**`Scripts/cores.lock` пустой.** Механизм проверки готов и работает: при
несовпадении SHA-256 сборка падает. Сами хеши нужно снять один раз на машине с
доступом к GitHub (`RECORD_HASHES=1 Scripts/fetch-xray.sh` и два других
скрипта) и закоммитить. Пока файл пуст, скрипты качают latest и громко
предупреждают — то есть поведение не хуже прежнего, но и не лучше, пока хеши не
записаны.

**HWID существующих установок не меняется.** Новые установки получают случайный
идентификатор, как и требует план. Но тем, кто уже подключался, старый
`IOPlatformUUID` переносится в Keychain как есть: тихая ротация выглядела бы
для панели новым устройством и могла бы упереться в
`x-hwid-max-devices-reached`, то есть просто отключить человеку VPN. Смена —
явное действие через кнопку «Сгенерировать заново» в настройках, с
предупреждением о последствиях.
